---
title: Transactional Outbox
subtitle: DBの更新とイベントの送信を食い違わせない
---
> Transactional Outboxは、DBの更新とイベントの送信を食い違わせないための書き方です。

## 二重書き込み
```flow LR
注文API -> [(orders)]: INSERT
注文API -> ブローカー: publish
ブローカー -> 在庫サービス
```
> 注文APIは、注文をordersテーブルに書きます。
> 続けて、同じ注文のイベントをブローカーへ送ります。
> 在庫サービスは、そのイベントを受けて在庫を減らします。

## 送信だけが失敗する
```flow LR
注文API -> [(orders)]: INSERT
注文API --> ブローカー: publish（失敗）
ブローカー -> 在庫サービス
```
> ところが、DBへの書き込みとブローカーへの送信は、1つのトランザクションにできません。
> [ブローカー]への送信だけが失敗することがあります。
> そうなると、注文はあるのに、[在庫サービス]には何も届きません。

## イベントもDBに書く
```flow LR
注文API -> [(orders)]: INSERT
注文API +-> +[(outbox)]: INSERT
group 1つのトランザクション: orders, outbox
```
> そこで、イベントもDBに書きます。
> [outbox]というテーブルに、イベントを1行で入れます。
> ordersとoutboxへの書き込みは、同じトランザクションで確定します。

## リレーが送る
```flow LR
注文API -> [(orders)]: INSERT
注文API -> [(outbox)]: INSERT
group 1つのトランザクション: orders, outbox
outbox +-> +リレー: 未送信の行を読む
リレー +-> ブローカー: publish
ブローカー -> 在庫サービス
```
> 別のプロセスの[リレー]が、outboxの未送信の行を読みます。
> リレーはイベントをブローカーへ送り、送れたら送信済みにします。
> 送信に失敗しても行が残るので、あとでもう一度送れます。

## 重複は防げない
```callout warn 受け手を冪等にする
リレーは、送ったあとで「送信済み」と記録する前に落ちることがある。
受け手はイベントのIDで重複を捨てる。
```
> ただし、リレーは同じイベントを2回送ることがあります。
> 送ったあとで、送信済みと記録する前に落ちた場合です。
> 受け手は、イベントのIDで重複を捨てるようにします。
