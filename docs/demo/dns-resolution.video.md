---
title: DNSの名前解決の流れ
subtitle: example.comのIPアドレスがわかるまで
---
> ブラウザがexample.comを開くとき、裏で何が起きているかを順に見ていきます。

## 名前解決はキャッシュから先に探す
```flow LR
@browser[ブラウザ] -> @stub[OSのスタブリゾルバ]: 名前を尋ねる
stub -> {OSにキャッシュがある?}
OSにキャッシュがある? -> @resolver[フルリゾルバ]: なければ問い合わせる
resolver -> {リゾルバにキャッシュがある?}
```
> [ブラウザ]は、まずOSにexample.comのアドレスを尋ねます。
> OSは自分のキャッシュを見て、答えがあればすぐ返します。
> なければ、プロバイダや社内のフルリゾルバに問い合わせます。
> フルリゾルバも、まず自分のキャッシュを確認します。

## フルリゾルバが上から順にたどる
```sequence
participants: フルリゾルバ, ルートサーバー, TLDサーバー, 権威サーバー
フルリゾルバ -> ルートサーバー: example.comはどこ?
ルートサーバー --> フルリゾルバ: .comの担当を紹介
フルリゾルバ -> TLDサーバー: example.comはどこ?
TLDサーバー --> フルリゾルバ: example.comの担当を紹介
フルリゾルバ -> 権威サーバー: example.comのIPは?
権威サーバー --> フルリゾルバ: IPアドレス
```
> キャッシュに答えがないとき、[フルリゾルバ]は[ルートサーバー]から聞き始めます。
> ルートサーバーは答えを知らず、.comを管理するサーバーを教えるだけです。
> 次に[TLDサーバー]に聞くと、example.comを担当するサーバーを教えてくれます。
> 最後に[権威サーバー]が、IPアドレスそのものを返します。

## 答えはTTLの間キャッシュされる
| 場所 | 覚えておく期間 | 効果 |
|---|---|---|
| フルリゾルバ | レコードのTTLまで | 同じ名前を聞く利用者みんなが速くなる |
| OS | TTLまで | 同じ端末からの再問い合わせが不要になる |
| ブラウザ | 独自の短い期間 | ページ内の通信がすぐ始まる |
> 返ってきた答えは、[フルリゾルバ]、OS、ブラウザの順に保存されます。
> どの場所も、レコードのTTLが切れるまでは同じ答えを使い回します。
> だから二回目からは、ルートサーバーまで聞きに行かずに済みます。

## まとめ
```callout ok 結論
まずキャッシュを探し、なければフルリゾルバがルート、TLD、権威サーバーの順にたどる。
```
> (+0) 名前解決では、まずキャッシュを探します。
> キャッシュになければ、フルリゾルバがルート、TLD、権威サーバーの順にたどります。
