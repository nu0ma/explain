ユーザーの同意を経て、アプリがアクセストークンを受け取るまで

アプリはユーザーのパスワードを受け取りません。認可サーバーが発行した認可コードを、アプリのサーバーがアクセストークンに交換します。

結論 トークンはブラウザを通らずにアプリへ届く

ブラウザが運ぶのは短命な認可コードだけです。アプリのサーバーは認可コードとクライアント認証情報を認可サーバーへ直接送ります。その応答でアクセストークンを受け取ります。

登場人物 4つの役割を分けて考える

役割 仕様での名前 この図での例
データの持ち主 Resource Owner ユーザー
データを使いたい側 Client アプリ
同意を取りトークンを出す側 Authorization Server 認可サーバー
データを持つAPI Resource Server リソースサーバー

ブラウザはリダイレクトを運ぶ通り道で、仕様上の4つの役割には含まれません。

安全のしくみ 各パラメーターが別の攻撃を防ぐ

パラメーター 防ぐもの
state 他人の認可コードを差し込むCSRF
redirect_uriの事前登録 認可コードを攻撃者のサイトへ送らせること
クライアント認証情報 盗んだ認可コードだけでトークンを得ること
PKCE（code_verifier） 認可コードの横取り。秘密を保てないSPAやモバイルアプリで特に必要
E

注意 認可コードは1回だけ使える

認可コードは短命で、使えるのは1回だけです。RFC 6749は有効期限を最長10分にするよう推奨しています。現在のOAuth 2.0 Security BCPは、すべてのクライアントでPKCEを使うよう推奨しています。
