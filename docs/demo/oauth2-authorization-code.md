---
title: OAuth 2.0の認可コードフロー
subtitle: ユーザーの同意を経て、アプリがアクセストークンを受け取るまで
cols: 2
---
アプリはユーザーのパスワードを受け取りません。認可サーバーが発行した認可コードを、アプリのサーバーがアクセストークンに交換します。

## 結論 トークンはブラウザを通らずにアプリへ届く {span=2}
```callout ok
ブラウザが運ぶのは短命な認可コードだけです。アプリのサーバーは認可コードとクライアント認証情報を認可サーバーへ直接送ります。その応答でアクセストークンを受け取ります。
```

## 全体の流れ 5者が3段階でやりとりする {span=2}
```sequence num
participants: ユーザー, ブラウザ, アプリ, 認可サーバー, リソースサーバー
== 認可リクエスト ==
ユーザー -> ブラウザ: ログインボタンを押す
ブラウザ -> アプリ: ログイン開始を頼む
アプリ --> ブラウザ: 認可サーバーへリダイレクトさせる（client_id, redirect_uri, scope, state）
ブラウザ -> 認可サーバー: 認可画面を開く
認可サーバー --> ユーザー: ログインと同意を求める
ユーザー -> 認可サーバー: ログインして同意する
認可サーバー --> ブラウザ: redirect_uriへリダイレクトさせる（認可コード, state）
ブラウザ -> アプリ: 認可コードとstateを渡す
== トークン交換 ==
アプリ -> アプリ: stateが送ったものと一致するか確かめる
アプリ -> 認可サーバー: 認可コードとクライアント認証情報を送る
認可サーバー --> アプリ: アクセストークンを返す（リフレッシュトークンも返す場合がある）
== リソースへのアクセス ==
アプリ -> リソースサーバー: アクセストークンを付けてAPIを呼ぶ
リソースサーバー --> アプリ: ユーザーのデータを返す
```

## 登場人物 4つの役割を分けて考える
| 役割 | 仕様での名前 | この図での例 |
|---|---|---|
| データの持ち主 | Resource Owner | ユーザー |
| データを使いたい側 | Client | アプリ |
| 同意を取りトークンを出す側 | Authorization Server | 認可サーバー |
| データを持つAPI | Resource Server | リソースサーバー |

ブラウザはリダイレクトを運ぶ通り道で、仕様上の4つの役割には含まれません。

## 安全のしくみ 各パラメーターが別の攻撃を防ぐ
| パラメーター | 防ぐもの |
|---|---|
| state | 他人の認可コードを差し込むCSRF |
| redirect_uriの事前登録 | 認可コードを攻撃者のサイトへ送らせること |
| クライアント認証情報 | 盗んだ認可コードだけでトークンを得ること |
| PKCE（code_verifier） | 認可コードの横取り。秘密を保てないSPAやモバイルアプリで特に必要 |

## 注意 認可コードは1回だけ使える {span=2}
```callout warn
認可コードは短命で、使えるのは1回だけです。RFC 6749は有効期限を最長10分にするよう推奨しています。現在のOAuth 2.0 Security BCPは、すべてのクライアントでPKCEを使うよう推奨しています。
```
